DomainScanner
Link copied to clipboard
object DomainScanner

Which ROS 2 domains have someone on them, without creating a node in each one: every DDS participant announces its presence (SPDP) by multicast on 239.255.0.1, port 7400 + 250·domain, every few seconds. It listens at once on the ports of all domains and records which IPs RTPS announcements come from. Requires the network to pass multicast (otherwise robots are found via KnownRobots or by setting their IP as a peer).

FoxgloveBridge
Link copied to clipboard
class FoxgloveBridge(val url: String, listener: FoxgloveBridge.Listener)

Client of the Foxglove WebSocket protocol (the foxglove_bridge one: foxglove.sdk.v1 since 3.x, foxglove.websocket.v1 in earlier ones; both are offered and the server chooses): instead of DDS, topics arrive over a websocket (also over the internet or mobile data). The messages travel in CDR, as in DDS, so they are read with the same message classes.

KnownRobots

object KnownRobots

Robots (machines running ROS 2) seen in each domain and their IPs. While multicast works they are learned automatically; afterwards they are used as unicast peers when connecting, so they are still found even if the Wi-Fi stops passing multicast. The logic is in Book (no Android, with tests).

RosNodes
Link copied to clipboard
object RosNodes

ROS 2 nodes on the network, like ros2 node list. DDS knows nothing about nodes: each rmw participant publishes on the DDS topic "ros_discovery_info" (no "rt" prefix) which nodes it has and the GIDs of their readers and writers. The latest from each participant is stored here; RosGraph cross-references it with the live endpoints (so participants that leave disappear).

RosStrings
Link copied to clipboard
object RosStrings

jros2 1.5.1 reads ROS strings (UTF-8) by turning each byte into a signed char: "í" (C3 AD) arrives as U+FFC3 U+FFAD. Here the bytes are recovered and decoded properly. Only for messages of jros2's classes: dynamic ones (DynCodec) already arrive properly decoded and passing them through here breaks single-byte characters like "ñ" (U+00F1).

TopicDiagnosis
Link copied to clipboard
object TopicDiagnosis

Why messages from a topic are not arriving, based on what is known from the graph: no connection, nobody publishes it (and maybe there is one with a similar name, e.g. with a namespace), it is of another type, or there is a publisher but nothing arrives (almost always incompatible QoS: a best effort publisher with a reliable subscriber, or a latched topic without transient local). Each case may come with a concrete fix. No Android: tested on the JVM.

TopicTypeRegistry
Link copied to clipboard
class TopicTypeRegistry

jros2 1.2.1 creates one DDS topic per (name, type) and never releases it during the node's lifetime. If a reader/writer is created with the same name and ANOTHER type, Fast DDS does not create the topic and jros2 passes a null pointer to create_datareader: SIGSEGV and the app crashes (verified on the JVM).

TopicVariables
Link copied to clipboard
object TopicVariables

Variables in topic names, like those of Foxglove layouts: a topic ${ns}/scan is /robot1/scan with ns = /robot1. They are resolved when subscribing or publishing (RosConnection), so they apply to everything at once (RViz, plots, indicators, buttons...). Changing a variable reconnects so that everything uses the new name.

ZenohLink
Link copied to clipboard
class ZenohLink(endpoint: String, domainId: Int, nodeName: String, listener: ZenohLink.Listener)

Connection to robots using rmw_zenoh_cpp: a Zenoh session in client mode against their router (rmw_zenohd). Follows the liveliness tokens for the graph and subscribes to topics; the data is the same CDR as over DDS, so RosConnection delivers it just like foxglove_bridge data. See ZenohNames for the names.

object ZenohNames

rmw_zenoh_cpp names (rmw_zenoh's docs/design.md): the data key expressions, the liveliness tokens with which each node, publisher, subscriber and service announces itself, and the ROS graph derived from those tokens. No Zenoh or Android dependencies, so it can be tested on the JVM.
